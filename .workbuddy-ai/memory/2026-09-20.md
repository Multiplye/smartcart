### THE BIG LESSON - headless `--window-size` does not set the layout viewport

I burned **three rounds of edits chasing a mobile overflow that did not exist.**

`chrome --headless --window-size=420,900 --screenshot=x.png` renders at the
default *desktop* width and then CROPS the image to 420px. The output looks
exactly like a page whose content overflows right — everything shifted and
clipped. I "fixed" it three times before measuring.

The measurement said: `viewport: 420`, `docScrollWidth: 420`, **zero
offenders**. The CSS had been fine the whole time.

**The correct check is CDP**: launch Chrome with
`--remote-debugging-port`, call `Emulation.setDeviceMetricsOverride`, then read
`getBoundingClientRect` from the page. Scripts written this session:

- `~/.workbuddy-ai/binaries/node/workspace/measure2.js` — reports
  `docScrollWidth` + every element wider than the viewport, by name.
- `~/.workbuddy-ai/binaries/node/workspace/shot.js` — true-layout screenshot.

Pass condition: **`docScrollWidth === viewport` and `offenders` is empty.**
Verified at 420px and 1440px: both clean.

For the screenshot, `Page.captureScreenshot({ captureBeyondViewport: false })`.
With `true` a full-page shot of a 36-product list shrinks to an unreadable sliver.

### Genuine CSS issues that measurement did surface

- **`min-width: 0` on the flex input.** A flex item will not shrink below its
  content size without it. The base `min-width: 180px` was holding the pill
  wider than a 420px viewport.
- **Never stack a pill into a column on mobile.** The old
  `@media (max-width: 600px) { .search-form { flex-direction: column } }`
  turned the pill into a tall capsule whose rounded ends no longer matched the
  controls inside. Kept the row; moved only Clear to its own line with
  `order: 3` + `width: 100%`.
- **Shortened the placeholder.** "Search products by name or description" was
  truncated mid-word on a phone. "Search products" fits everywhere; the full
  wording moved to `aria-label` so screen readers still get it.
- Gave `.filter-bar` side margins on mobile (`margin: -34px 16px 0`) so the
  card's rounded corners are visible instead of bleeding off the screen edge.

### The icons took three render passes to get right

Invisible in source, obvious at 3x zoom on a screenshot:

1. **Art too small in its box.** The first drawing used about `x 7..41` of
   48. At 34px in a 72px chip the icon looked lost. Now draws to
   `x 4..44` and renders at 38px in a 68px chip.
2. **Stroke clipped by the viewBox edge.** The phone's outer signal arc was
   centred at `x=36` radius `14` in a 48-wide box: `36+14+1.2 = 51.2`, so
   it ran off and was sliced. Moved to centre `28` radius `11` = `40.2`.
   **Check the outer edge (`centre + radius + strokeWidth/2`), not the
   centre line.**
3. **Centre the union, not the main object.** Phone body at `7..25` plus
   arcs reaching `40` spans `7..40`, midpoint 23.5 — so the phone must sit
   *left* of centre or the arcs leave the box.

Also removed a floating "clothes rail" dash under the hanger (no context,
read as a stray mark), widened the hanger hook (a tight loop read as `?`),
drew the roof and walls as one continuous path (a chevron roof overhung the

## Step 29 - Scroll animations across the site

User: *"i need you to keep beautiful animation accross the webpage"*.

### What existed already

Only two places animated: the hero illustration (hand-written keyframes)
and the recommendations page (an `ai-rise` / `ai-card-in` entrance with an
inline `--rec-delay`). Everything else — the product grid, category cards,
trust bar, AI section, cart, footer — appeared statically.

There was also a `fadeUp` animation on `.product-card` and `.hero-content`
that fired **on page load**, not on scroll. Anything below the fold
therefore animated while nobody was looking, so the effect did nothing.

### The new system

Three pieces:

1. **`src/hooks/useReveal.js`** — IntersectionObserver-based. Returns
   `[ref, isShown, style]`. Elements reveal only when they actually enter
   the viewport.
2. **`src/components/Reveal.jsx`** — a thin wrapper so call sites read
   `<Reveal className="product-card" delay={i * 90}>`, not three lines of
   ref/class/style plumbing.
3. **`.reveal` / `.reveal-in` / `.reveal-lg` / `.reveal-fade`** in App.css
   — opacity + translateY transitions, with `--reveal-delay` for stagger.

Applied to: trust bar (4 cells, 70ms apart), section headings
(`variant="lg"` for a longer 40px rise), the three category cards
(110ms apart), home product cards (90ms), the products page grid
(70ms, **capped at index 8** — an uncapped stagger on a 36-item list
would leave the last card waiting 2.5s and read as broken), the AI
section (text leads, visual follows 120ms), the cart header, and the
"View All Products" button.

### THE DESIGN RULE THAT MATTERS: hide only as an upgrade

`.reveal` starts at `opacity: 0`. If the observer never fires, the page
is **blank**. So the hook never renders the hidden class — it adds
`.reveal` to the element *from inside the effect*, after checking:

- `typeof IntersectionObserver !== "undefined"`
- `prefers-reduced-motion` is not set

Both conditions are resolved during render (not in the effect) and folded
into `isShown`. If either fails, the effect returns early, the class is
never added, and the element stays visible. A JavaScript error above the
hook therefore leaves the page readable rather than empty.

A second `@media (prefers-reduced-motion: reduce)` rule forces
`.reveal { opacity: 1 }` as belt-and-braces.

### Two bugs the linter and my own review caught

- **`setState` synchronously inside an effect** — eslint's
  `react-hooks/set-state-in-effect` flagged the reduced-motion branch,
  which set `shown` to true immediately. Fixed by computing the condition
  during render and folding it into the returned value, so the effect's
  only job is observing. Cleaner *and* one render cheaper.
- **`{...rest}` spread after `className`/`style`** in `Reveal.jsx` — a
  caller passing their own `className` would have silently overwritten the
  reveal classes and the element would never animate, with no error. Fixed
  by spreading `rest` FIRST.
- Also guarded the StrictMode double-effect: the cleanup removes `.reveal`,
  so the second pass would have re-hidden an already-revealed element and
  made it blink.

### Removed a conflicting animation

`.product-card` had `animation: fadeUp 0.6s ease forwards` — a load-time
animation fighting the new scroll transition over the same two properties.
Deleted, with a comment explaining why, and replaced the generic
`transition: var(--transition)` with an explicit transform/shadow/border
set.

### Micro-interactions added

- Product image `scale(1.06)` on card hover (0.5s).
- One shared `button:active { transform: scale(0.97) }` rule for every
  button, guarded with `:not(:disabled)` — a disabled button that still
  squashes looks broken.
- Cart count badge pops when the number changes. Driven by a
  `useRef` of the previous value, because the count alone cannot tell a
  real change from an unrelated re-render. The class is removed on a
  420ms timer so the animation can retrigger.
- Nav underline switched to a 0.28s cubic-bezier wipe.

### Verified — `check-reveals.js` is the tool to reuse

It scrolls the page to the bottom in steps, then reports how many
`.reveal` elements are still under 0.95 opacity. `stuckCount` must be 0.

```
desktop 1440   before scroll: total 12, inView 4
               after: revealDone 16, stuck 0, offenders []
mobile  420    before scroll: total 16, inView 0
               after: revealDone 16, stuck 0, offenders []
REDUCED=1      before scroll: total 16, inView 16   <-- correct:
               everything visible immediately, nothing hidden
```

Also captured **mid-animation** frames with `shot-mid.js` (parks the page
below the target, scrolls in, shoots after ~60-120ms). Those confirmed the
stagger visually — card 1 settled, cards 2-4 still rising.

### New helper scripts
- `check-reveals.js <width> [path]`, `REDUCED=1` to emulate reduced motion.
- `shot-mid.js <url> <width> <out> <selector> [delayMs]` — mid-transition
  frame, which is the only way to see a stagger in a still image.

### Skill
Created **`scroll-reveal-animation`** covering this whole workflow.

## Step 30 — Journey check finds a blank page, then a scroll that stops short

Commit `17f97c4`. Ran the backend suite (430 tests, 0 failures) and then
walked the real user journey in a browser. The browser walk is what found
both of these — neither is visible from reading the code.

### Bug 1 — an unknown URL rendered nothing at all

`walk-journey.js` step 8, for `/definitely-not-a-real-page`:

```
{"bodyLength":0,"hasNavbar":false}
```

**No catch-all route.** Every `<Route>` had an explicit path, and the
navbar is supplied *per page* by `PageLayout` rather than wrapped around
the routes — so a URL matching nothing had nothing to render it. A typo
gave a white screen with no way back.

Fixed: `NotFound.jsx` (wrapped in `PageLayout`, so it keeps the navbar),
registered as `<Route path="*" ...>` **last**, three destination links
(catalogue first — a mistyped `/product/12` is usually a shopper, not
someone wanting the landing page), and a decorative echo of the
`CategoryIcon` row.

**Lesson: any app whose navbar lives inside pages needs an explicit
catch-all. The blank screen is the symptom of a missing route, not of a
missing component.**

### Bug 2 — `/#auth` scrolled to the login form and stopped 580px short

`check-auth-jump.js` said the click *worked* (`/#auth`, `Welcome Back!`
visible) but measured `authTop: 491`. Tracing position over time:

```
t=1.0s  y=3918   auth  955px down the viewport
t=1.5s  y=4293   auth  580px down   <- stopped for good
...unchanged for the next 6.5 seconds...
maxScroll 5343   authOffsetTop 4873   <- 530px of travel still available
```

So it was not a clamp. `ScrollManager` polled for the element, scrolled
once, and cleared its own timer. Two causes:

1. **The page was still growing.** Product images load asynchronously;
   each arrival pushes everything below it down. It scrolled to where the
   form was, then the form moved.
2. **It gave up after 500ms.**

Fix: re-aim every tick from the element's live rect, and stop only after
the target has held still for 200ms. First scroll stays `smooth`; later
corrections are `auto` — a smooth animation fighting a shifting page
reads as a jitter. Also clamped to `scrollHeight - innerHeight`.
Non-hash navigations changed to `behavior: "auto"` so a route change does
not animate the old page sliding past.

Result: `y=4873`, `authTop: 0`. All five navbar hash targets pass
(`#products`, `#categories`, `#about`, `#auth`, `#contact`), and a plain
route change still resets to 0.

**`#contact` stops at `top: 225` and that is correct** — it is in the
last screenful, and `y` equals `maxScroll` exactly. *Always compare a
"short" scroll against `maxScroll` before calling it a bug.*

### Bug 3 — logged-out checkout told you to go find the login form

Copy said "head to the home page and log in" and linked to `/` — top of a
long page, form out of sight. Now "Log In or Register" → `/#auth`.

### New helper scripts
- `walk-journey.js` — 8 real steps, collects console errors + failed
  requests. **Run this after any routing or data-flow change.**
- `check-auth-jump.js` — asserts a hash link lands with the target near
  the top of the viewport.
- `trace-scroll.js` — samples `scrollY` every 500ms for 8s. This is what
  distinguished "settling" from "stopped for good".
- `check-scroll-targets.js` — every navbar hash target, from another route.
- `check-contact.js` — compares a short scroll against `maxScroll`.

  works, `127.0.0.1:5173` is refused. Point CDP scripts at `localhost`.
- Reusing a CDP port after a crashed run gives `ECONNREFUSED`; each

## Step 31 — API returned HTML on errors it did not anticipate

Commit `878e7ea`. Found while closing out the last unchecked edge case
from the journey: a non-numeric product id.

```
GET /api/products/abc
-> <!doctype html><html lang=en><title>404 Not Found</title>...
```

Every route in `app.py` already returns JSON, and most return a JSON
error of their own. But those only cover what the route anticipates.
`/api/products/<int:product_id>` — the `int` converter does not match
`"abc"`, so **no route is selected at all** and Flask serves its
built-in HTML error page.

The React frontend copes (a failed `.json()` lands in the same catch as
any other error), which is exactly why this hid for so long. Anything
else — curl, a test, a second client — reports a **parse error** instead
of "not found", pointing at the wrong problem.

Also worth noting: **the frontend showing a correct error page is not
evidence the API is correct.** It was swallowing the wrong shape.

### Fix

Handlers for 400 / 404 / 405 / 500, all returning `{"error": ...}`.

Two deliberate choices worth keeping:
- The generic 404 says just `"Not found."` — not whether it was the
  route or the id. Naming which one tells someone probing the API how
  it is laid out.
- The 500 handler returns no exception detail. A stack trace in an HTTP
  response is how internal file paths and query text reach a client's
  logs.

Route-specific errors still take precedence, so the more useful message
survives:
```
/api/products/99999  -> {"error": "Product not found."}   (from the route)
/api/products/abc    -> {"error": "Not found."}           (from the handler)
/api/does-not-exist  -> {"error": "Not found."}
DELETE /api/products -> {"error": "Method not allowed for this URL."}
```

### Result
- 430 backend tests still pass
- browser journey unaffected: 0 console errors, 0 failed requests
- all invalid routes return JSON

### Edge cases now confirmed handled
| URL | Frontend result |
|---|---|
| `/product/abc` | "Not Found" + message, navbar intact, no throw |
| `/product/99999` | same |
| `/some-bogus-url` | 404 page, navbar intact |
| `/api/products/abc` | JSON `{"error": "Not found."}`, 404 |

**No frontend change was needed for the bad product id** — `ProductDetail`
already handled it. The bug was purely that the API answered in the
wrong format.
